# Competition runtime

| Folder | Runtime responsibility |
| --- | --- |
| `aeacus/` | Readable check definitions, native probes and supporting modules for six defended guests |
| `shop/` | PHP catalog, order submission, order history and schema |
| `forum/` | Forum database structure; the phpBB engine is an external dependency |
| `score01/` | Functional service probes, lifecycle/SLA accounting, scoreboard, portal and task acceptance |
| `red-team/` | Controller, profiles, CALDERA integration, guest workers/notices and scoring bridge |
| `running-configs/` | Sanitized service/application snapshots and portable hypervisor examples |
| `materials/` | Participant handout with blank credential fields |

The flat Python layouts preserve sibling imports. Controller `legacy/` files and guest recovery workers remain because active modules use them. Scenario builders, acceptance, broad solve/reset tools and installers belong in `../preparation/`.

These are review paths, not an installation hierarchy. Service units refer to their intended guest paths. Do not deploy the entire directory by copying it over a VM.

Encrypted `scoring.dat` files are retained privately. This candidate does not claim those artifacts were regenerated from the shown definitions. The mail definition is pre-forensics history; final additions are generated by preparation scripts. DC01 uses a source generator in `../preparation/image-builds/dc01/competition/`. The workstation red-team agent source is locally authored source, not a freshly verified export of its installed directory.
